- **Core Downloads Are Pinned (`internal/core/binary_downloader.go`):**
  - `pinnedCoreHashes` was an empty map with an example comment — the whole supply-chain guard existed but guarded nothing. Now pinned (hashes computed from archives downloaded from the canonical GitHub release URLs, and cross-checked byte-for-byte against the bundled binaries, which are genuine upstream builds):
    - sing-box v1.14.0 windows-amd64: `3ffb56267da14e287be48bd10cf7e6505260125bad940b75101fbb4d5d58e5d6`
    - Xray-core (latest-URL, v26.3.27 at pin time): `d004c39288ce9ada487c6f398c7c545f7d749e44bdfdd59dbc9f865afba4e1ad`
    - openvpn-portable 2.5.8-19: `0019dfc4b32d63c1392aa264aed2253c1e0c2fb09216f8e2cc269bbfb8bb49b5`
  - sing-box publishes **no** checksum sidecar (verified: `.sha256`, `.sha256sum`, `.dgst` all 404) — the pin is the only anchor for that core. Xray publishes `.dgst` in openssl format.
  - `fetchSidecarSHA256` now also tries `.dgst` and scans the whole body for the first 64-hex token. The old parser read `fields[0]`, which in `SHA2-256= <hash>` format is the literal string `MD5=` — so Xray's real sidecar never parsed. One-line bug, whole-chain impact.
  - `verifyDownloadedArchive` order changed: upstream sidecar (canonical origin, HTTPS) **first**, pin second. Rationale: "latest" URLs change content on every upstream release, so a pin for such a URL is *expected* to go stale; refusing that update trains users to enable unverified mode. A sidecar from github.com still defeats a compromised mirror, and a pin that mismatches with no sidecar to vouch for the change still fails closed.

## [2026-10-13] - 🐛 Fixed & ✨ Added (Resolver Choice Under DPI, Dead-Config Cleanup, WebView2 Rendering Levers, Idle Core Sweep, Honest Latency)

Second real session log (352 lines, 23:28–23:37) — and this one is mostly proof that the 2026-10-11 fixes work: ANSI codes gone, `×N` merge notices, rate-cap notices, `System Proxy fallback … failed to start`, `Auto-Failover was not used (disabled in settings)`, and the Wintun pre-flight choosing TAP up front. Four defects survived that log, plus the adopted-idea backlog.

- **The Resolver Is Chosen Per Primary Type (`internal/parser/parser.go`):**
  - The log's WireGuard session produced ~200 lines of `dns: lookup failed … read tcp 192.168.1.103:xxxxx->1.1.1.1:443: wsarecv: An existing connection was forcibly closed` — the configured DoH resolver being reset by the network, while the same machine resolves through its router (192.168.1.1) with no tunnel up.
  - sing-box 1.14 has **no fallback chain**: `dns.final` and `dns.rules[].server` both reject a list (verified against the bundled core). So the app picks: `dns-direct` (the OS resolver) as the final resolver for a Layer-3 primary, `dns-remote` (through the tunnel) for a proxy primary, and `route.default_domain_resolver` is now set to the *same* value — the split between the two is what made dial-time lookups ignore the route setting.
  - `dns-fallback` — written into every generated config and referenced by nothing — now has a job: it resolves the tunnel endpoint for Layer-3 profiles, where a poisoned local resolver is the failure mode worth avoiding.
  - The earlier `detour: "direct"` for Layer-3 was a startup FATAL (`detour to an empty direct outbound makes no sense`, sing-box #2778/#2803) that `sing-box check` does **not** report; the omission-based form is kept and now guarded by a test that boots the core.
- **Incomplete Shadowsocks Links Are Rejected at Parse Time (`internal/parser/parser.go`):**
  - `parseShadowsocksOutbound` emitted `"method": ""` / `"password": ""`, and both cores died with messages that named neither the profile nor the missing field (`initialize outbound[2]: unknown method:`, `Shadowsocks password is not specified`). Now the parser refuses the link with an actionable reason.
- **One Crash Handler Instead of Two (`internal/core/engine.go`):**
  - The primary and fallback `SetOnExit` bodies were hand-copies, and the fallback logged the identical `Core process crashed: …` line twice per death. Extracted into `handleCoreExit(operationID, err, cleanup)`; the only difference (clear proxy vs flush network) is a parameter.
- **Wintun: Ghost ≠ Live Adapter (`internal/protocols/{openvpn,wintun_windows,wintun_ghost_other}.go`):**
  - New `NexVPNWintunAdapterLive` answers the question that actually blocks an allocation. The pre-flight was waiting on *any* trace of our names — including a registry-only ghost, which holds no handle and can never be waited out — so every OpenVPN connect burned the full 6 s budget and still fell back to TAP.
- **Honest Latency (`internal/parser/parser.go`, `internal/core/batch_tester.go`):**
  - `MeasureLatency`: a discarded warm-up dial plus the minimum of two timed TCP round trips. The server list used to store `TCPPing`'s result, which demands a TLS handshake on port 443 and reports failure — so every `ip:443` Reality node was shown as dead. `TCPPing` stays where it belongs: the smart-ping path, where refusing the handshake really is the answer.
- **Idle Core Sweep (`internal/core/engine.go`, `app_watchdog.go`):**
  - `Engine.SweepIdleCores()` refuses to run in `connected/connecting/disconnecting` — `CleanupStaleCores` kills every registered PID, so an unguarded timer would have dropped live tunnels. Scheduled every 2 minutes; a core that outlived its Disconnect no longer holds 10808 until the next app restart.
- **WebView2 Rendering Levers, Reachable Without a Window (`main.go`, `app_diagnostics.go`, `internal/config/store.go`, `internal/sysproc/dialog_*.go`, `internal/tray/*`):**
  - `webview_disable_gpu` and `webview_disable_code_integrity` feed `windows.Options.WebviewGpuIsDisabled` / `WebviewDisableRendererCodeIntegrity`, read once before the webview exists (both default false = today's behaviour).
  - The tray gained **Open startup report** (Notepad on the launch diary) and **Turn GPU rendering off/on (restart to apply)**, labelled from the persisted state — the tray is the only surface left when the window cannot be drawn.
  - `sysproc.ShowFatalDialog` / `ShowNoticeDialog` (user32 `MessageBoxW`) report the fatal `wails.Run` error and the restart requirement outside the app window.
- **Single Instance (`main.go`):** `SingleInstanceLock` with `com.nexvpn.desktop`; a second launch now raises the existing window instead of fighting it for 10808, `config.json` and the kill-switch rules. Logged as `launch/second-instance-suppressed`.
- **Settings UI + i18n (`frontend/src/pages/Settings.tsx`, `types/index.ts`, `lib/i18n.ts`):** both rendering levers as rows in “System & Cores”, with the restart caveat and the sandbox trade-off stated in the description (fa + en).
- **Docs (`docs/TROUBLESHOOTING_FA.md`):** a user-facing runbook keyed to the exact strings the app now emits — black window, `Server is not reachable`, `Auto-Failover was not used`, `None of the N backup servers answered`, TUN fallback variants, `WINTUN_IN_USE`, the DoH-reset signature, the Telegram/system-proxy clash, and what to attach to a report.
- **Tests (`internal/parser/{dns_startup_test.go,latency_and_ss_test.go}`, `internal/core/idle_sweep_test.go`):**
  - `dns_startup_test.go` **boots the bundled core** on relocated ports to assert the resolver policy for both primary types — `sing-box check` passes configs the service then refuses, which is exactly how the WireGuard engine shipped broken.
  - `latency_and_ss_test.go` covers a plain listener that never speaks TLS, a refused port, and the three incomplete `ss://` shapes.
  - `idle_sweep_test.go` pins the state guard. No test drives `handleCoreExit` or `Stop()` end to end: both clear the Windows system proxy, and a unit test must not change machine-wide state.

## [2026-10-11] - 🐛 Fixed (DNS Deadlock in the WireGuard Engine, Fake-IP Cache, Silent Fallback, Cooldown for Dead Servers, Log Hygiene)

Findings came from a real 24-minute session log (673 lines, 132 KB) covering Psiphon, Sing-box WireGuard, Sing-box TUN and OpenVPN/TunnelBear.

- **DNS Resolution No Longer Depends on the Tunnel It Enables (`internal/parser/parser.go`):**
  - `dns-remote` and `dns-fallback` were always detoured through `primaryTag`. For a Layer-3 primary (WireGuard) the core must know the real IP *before* a packet can enter the tunnel, so every lookup timed out (`dns: lookup failed … context deadline exceeded`, 10s each, ~90 lines in two minutes). A new `outboundIsLayer3` test now routes DNS for those profiles over `direct`; proxy-style primaries (VLESS/VMess/Trojan/SS/Hysteria2/TUIC) keep the tunnel detour so nothing leaks.
  - Same deadlock removed from the WARP-on-WARP generator (`detour: "proxy"` → `"direct"`).
  - `dns.timeout` set to `3s`: sing-box 1.14 rejects a per-server `timeout` (`unknown field`) but accepts the `dns` block option — pinned by `TestSingBoxDNSQueryTimeoutIsBounded` and validated against the bundled core.
- **Fake-IP Store Persisted (`internal/protocols/singbox.go`):**
  - `experimental.cache_file {enabled, store_fakeip, path}` is injected at spawn time (`injectCacheFile`), which removes the `router: missing fakeip record` burst: Windows keeps the previous session's synthetic `198.18.x.x` answers in its DNS cache and a fresh core could not map them back to names, so those connections were dropped.
  - The path lives under the writable data directory (`singBoxCachePath`), not the core's `-D` bin folder, which is read-only under Program Files. An imported config that already sets `cache_file` is left alone.
- **TUN → System Proxy Fallback Can No Longer Fail Silently (`internal/core/engine.go`):**
  - `dispatcher.Decide` and the fallback adapter's `Start` returned errors that were thrown away, so the log read "Auto-falling back to System Proxy mode…" followed by 37 silent seconds and the *original* TUN error. Both are now logged, written to the diary (`fallback-decide-fail`, `fallback-start-fail`) and appended to the final message; the port-busy abort records the same note.
- **Bounded Wait Instead of Guessing (`internal/protocols/openvpn.go`):**
  - A fixed `Sleep(900ms)` after clearing a leftover NexVPN Wintun adapter was replaced with `waitForNexVPNWintunAdaptersGone` (poll every 500ms, 6s budget). When the pool is still held and a TAP adapter exists, the driver is chosen up front instead of paying for a full TLS handshake that OpenVPN then aborts with `WINTUN_IN_USE`.
- **Dead Servers Get a Cooldown (`internal/config/store.go`, `internal/core/{engine,autoselect}.go`, `app.go`):**
  - New engine hook `OnServerHealth(profileID, healthy, reason)`: failure is reported on verify-fail, on a mid-session drop (except a local TUN fault) and on health failover; success is reported at `StateConnected`.
  - `Store.RecordProfileFailure` / `ClearProfileFailure` / `ProfileIsCoolingDown` (10-minute window, rune-safe reason truncation, debounced writes) persist the verdict onto the profile so it survives a restart.
  - `RankFailoverCandidates` demotes cooled-down servers below every healthy peer instead of deleting them, `FindFastestProfile`'s "nothing answered" guess avoids them, and "no backup reachable" now states how many were on cooldown.
- **Reconnect Budgets Stop Refilling Themselves (`internal/core/engine.go`):**
  - The three "max attempts reached" branches reset the counter to zero, which is how every failure reported `attempt 1/3` forever and a dead subscription looped unbounded. The counter is now refilled only by a successful connection or an explicit `Disconnect`, and the ceiling messages say so.
- **Failover Silence Ended (`internal/core/engine.go`):**
  - When a verify failure cannot trigger failover (switched off, no handler, no profile id) the reason is logged and written to the diary (`failover-not-armed`) — previously six failing attempts produced no failover line at all.
- **The App Stopped Reacting to Its Own Adapter (`internal/sysproc/netwatch.go`, `app_watchdog.go`, `internal/config/store.go`):**
  - `interfaceFingerprint` excludes NexVPN's own adapters (new `config.IsNexVPNAdapterName` / `AdapterNamePrefix`), so creating or destroying the TUN no longer reports "Network change detected"; the extracted `fingerprintInterfaces` is unit-testable.
  - The watchdog only announces and re-validates a tunnel when a session is actually connected (`SessionProtocol`), and records `change-no-session` otherwise.
- **Core Log Hygiene (`internal/protocols/{corelog,singbox,xray}.go`):**
  - ANSI colour escapes are stripped before anything is stored, so the log view, the diary and the report file are plain text.
  - `coreLogMerger` folds runs of identical core lines into one entry plus a `×N` summary (level preserved, window 10s, flushed on process exit). A 24-minute session that produced ~670 lines is now a few dozen, and the meaningful lines are no longer pushed out of the engine's 1000-entry buffer.
  - `SingBoxAdapter.Stop` / `XrayAdapter.Stop` log "stopped" only when a process was actually running; the same disconnect used to print it four times.
- **Dual-Routing Is Now a Choice (`internal/config/store.go`, `internal/core/engine.go`, `frontend/src/{types/index.ts,pages/Settings.tsx,lib/i18n.ts,lib/api.mock.ts}`):**
  - New `tun_system_proxy` setting (`dual` by default, so no existing install changes behaviour; `tun_only`). Setting the machine-wide HTTP proxy next to a working TUN adapter breaks applications that hand non-HTTP traffic to it — the log's `parse "http://2001:b28:f23f:f005::a:443": invalid port` storm is Telegram's IPv6 DNS queries arriving at the HTTP inbound.
  - The routing mode actually applied is now written to the diary (`connect/routing`).
- **Tests (`internal/parser/dns_routing_deadlock_test.go`, `internal/protocols/corelog_test.go`, `internal/config/server_failure_test.go`, `internal/core/server_cooldown_test.go`, `internal/sysproc/netwatch_fingerprint_test.go`):**
  - 30 new cases, including generated configs checked against the bundled `sing-box 1.14.0` binary (`sing-box check`) for both the WireGuard and VLESS DNS topologies and for the injected `cache_file`.
